## Frontend und Backend Datenfluss

### Authentifizierung

Bevor die grundlegende Kommunikation zwischen Front- und Backend funktionieren kann, ist es wichtig, dass sich der User authentifiziert, sodass das Backend die nötigen Daten zur Verfügung stellen kann. Sobald sich ein User authentifiziert, und die Session im Backend als gültig überprüft wurde (Username und Passwort Hash stimmen überein), wird eine SessionID erstellt, die in der Datenbank gespeichert wird und einem bestimmten User zugehörig ist. Diese SessionID wird danach an das Frontend zurückgesendet, was diese ID als Cookie lokal speichert und bei jeder Request aus dem Frontend mitschickt, wodurch der User eindeutig identifiziert werden kann.

### Datenfluss im Frontend

Nehmen wir an, der User öffnet das Dashbaord. Hierzu sind viele Datenabfragen wichtig, eine davon: welchen Score hat der User? Um diese Request erfolgreich zu erfüllen, wird diese Request erstmal über das Framework TanStackQuery abgehandelt. Dieses Framework erstellt einen Cache, cached und validiert somit bestimmmte Datenpunkte die abgefragt werden: Sollte ein User seinen Score abfragen, so muss dieser nicht vom Backend geliefert werden, sondern kann direkt aus dem Cache angezeigt werden. Somit können Seitenwechsel, wenn der User zum Beispiel von "Dashboard" auf "Hebel" und wieder zurückgeht, ohne erneute Backend Anfrage abgehandelt werden. Dieser Cache gilt für 30 Sekunden als valide, danach würde eine erneute Backend Anfrage ausgeführt, um die richtigen Daten anzuzeigen. Sobald der User eine Änderung macht, wird der gesamte Cache invalidiert, damit solche Änderungen sofort angezeigt werden.

Im Frontend ist zudem die Datei `frontend/src/api/generated.ts`, welche den API Contract vom Backend direkt ins Frontend einbindet. Damit die beiden Stacks trotzdem lose gekoppelt sind, wird hierbei nicht eine gemeinsame Datei zwischen den beiden genutzt. Die Datei wird jeweils durch ein Skript aus der von Backend zur Verfügung gestellten backend openapi.json bereitgestellt.

### Datenfluss im Backend

Wie gewöhnlich kommen API Anfragen im Backend zuerst bei der Middleware an, bei der wir Fastify als Framework. Davon nutzen wir unter anderem Helmet, um sicherzustellen, dass keine böswilligen Skripte ausgeführt werden können, sowie Fastify/Rate-Limit, wodurch wir Anfragen von einer IP auf 120 Anfragen einschränken, um einen DDOS Schutz zu haben und einen Cookie Parser, der mitgeschickte Header ausliest, wie z.B. die unter Authentifizierung genannte SessionID. Diese SessionID wird mit der Datenbank abgeglichen, wobei bei erfolgreicher Zuweisung die Variable userId an das Anfrage Objekt angehängt wird, welches bei jeder Backend internen Anfrage angehängt wird. Mittels dieser kann jede Funktion zuordnen, von welchem Account die Anfrage kommt.
Funktionen können dann jeweils je nach Anfrage ihre Logik ausführen. Um zum Beispiel zurückzukehren, muss jetzt der Score berechnet werden. Diese Daten liegen zum einen in den Datenbanktabellen Samples (Gesundheitsdaten) und Users (biologisches Geschlecht und alter). Mithilfe der jeder Funktion mitgeliefterten UserID können diese darauf passend abgefragt werden. Diese Anfrage könnte man zum einen mit jeweils selbstgeschriebenen SQL Abfragen machen, wir haben uns aber für das Framework Drizzle entschieden: So können wir Drizzle Funktionen nutzen, die z.B. so aussehen: `db.select().from(samples).where(eq(samples.userId, user.id))`. Sollte ein Fehler drin sein, sieht man das damit sofort, und nicht erst, wenn während der Laufzeit eine solche Abfrage gemacht wird und ein SQL Statement failed. Zudem ist man so mit Drizzle auch automatisch gegen SQL Injections geschützt. Nach dieser Abfrage und Kalkulation wird dann das Ergebnis von Fastify als JSON Format zurückgegeben.

## Designentscheidungen

In jedem Teilaspekt von Software Entwicklung gibt es Designentscheidungen - so werden hier die wichtigsten benannt. Im Allgemeinen wurden Architekturentscheidungen so getroffen, dass sie zugunsten der Datensicherheit sind (und DSGVO-konform sind), deterministische mathematische Testbarkeit bieten und eine gute Wartbarkeit geben.

### Server Side Session mit PostgreSQL anstatt von Stateless JWTs im LocalStorage

Eigentlich werden in fast allen Webanwendungen, auch die, die wir zuvor im Rahmen der DHBW gebaut haben, zur Authentifierung Stateless JWT-Tokens genutzt. Im Rahmen von diesem Projekt haben wir die oft als altmodisch gesehene Alternative von Server Side Sessions genommen. So wie oben im Authentifizierungsflow beschrieben läuft jede Anfrage zuerst über die Sessions Datenbanktabelle, da der mitgeschickte Header auf die SessionID überprüft werden muss. JWT Tokens dagegen können einfach durch einen mathematischen Algorithmus ohne Datenbank überprüft werden. Während dies schneller ist, haben wir mit einer GEsundheitsplattform besondere Anforderungen an uns gestellt, und dazu gehört auch die sofortige Wiederrufbarkeit. Sollte der User sein Passwort zurücksetzen, invalidiert das alle offenen SessionIDs, wodurch auch bei zuvor angemeldeten Browsern eine weitere Abfrage unmöglich wird. Einmal verschickte JWT Tokens können bis zu ihrem Ablaufdatum weitergenutzt werden.
Alternativen wären hierzu JWT Tokens mit kurzer Nutzungsdauer gewesen, oder eine JWT Token Blacklist. Während ersteres die trotzdem keinen sofortigen Widerruf möglich macht, benötigt das zweite genauso wie unsere Lösung eine Datenbankanfrage bei jeder API Request.

### Append Only für Messwerte; keine veränderlichen Datensätze

Das Backend überschreibt keine Datenwerte, sondern fügt sie immer als neue Einträge der Datenbank zu. Zwar wäre es hierfür einfacher, die jeweiligen Daten zu überschreiben, da ansonsten Tabellen jeweils immer größer werden - so hätte man ja trotzdem noch durch die Score Datenbanktabelle jeweils den Score für jeden Tag. Trotzdem haben wir uns für diesen SChritt entschieden, da uns das Vertrauen in die Plattform das wichtigste ist. So ist es jetzt ganz einfach nachzuvollziehen, warum der Score an irgendeinem Tag seit Kontoerstellung wie errechnet wurde. Würde die Score Berechnung an aktuelle wissenschaftliche Erkenntnisse angepasst werden, so kann man das auch ohne Probleme rückwirkend zu machen, ohne dabei bestimmte Daten nicht mehr zu berücksichtigen. Zudem können bei möglichen, nicht bedachten Fehlern in der Vergangenheit bei der Score Berechnung ohne Probleme neu berechnet werden - ohne Vertrauensverluste zu erleiden. Als Trade-Off könnte man neben der höheren benötigten Speicherkapazität zudem bei Datensicherheit sehen: würden wir nur den Score speichern, so würde ein Datenverlust nur die heutigen Gesundheitsdaten freisetzen, nicht die der letzten drei Jahre. Da wir die Anwendung von Grund auf jedoch so gebaut haben, dass Gesundheitsdaten sicher gespeichert werden, bleiben wir bei dieser Entscheidung.

## Tests- und Qualitätssicherungskonzept

### Tests

Bei Tests werden bei aktuellen Projekten sehr oft Mocks genutzt, um die Funktionalität zu nutzen. Sie fälschen Datenbankabfragen mit Dummys, und haben den Vorteil, dass Tests bemerkenswert schneller laufen, da keine tatsächliche Datenbankabfrage durchgeführt wird. Das Problem dabei ist, dass man damit nicht die Realität testet: Zwar können die Tests grün durchgehen, wenn in der laufenden Umgebung dann die Datenbank jedoch andere Datentypen gespeichert hat, können die Tests zwar durchlaufen, es in der laufenden Umgebung aber trotzdem zu Problemen kommen. Es ist trotzdem natürlich wichtig, auch isolierte Funktionen zu testen, auch ohne Abfrage einer Datenbank: Unsere Unit Tests laufen somit ganz ohne extra Input, somit wird die isolierte Funktionsweise getestet. Integrationstests dagegen laufen jeweils immer gegen eine tatsächliche PostgreSQL 16-Instanz. (lokal über Docker Compose, in Github Actions über Service Contatiner). Die letzte Ebene bilden Frontend Unit- und Barrierefreiheitstests sowie E2E Browsertests und Playwright.

Als Fundament nutzen wir sogenannet Golden Master Tests: Diese testen den Mittelpunkt unserer gesamten Software: Die Score Engine. Sollte sie falsche Ergebnisse liefern, könnten User Vorteile bekommen, die ihnen nicht zu stehen - und so nicht nur das Vertrauen der Konsumenten, sondern auch der B2B Partner untergraben. Deswegen füttern wir die Engine mit vordefinierten JSON Dateien, und wissen exakt welches Ergebniss rauskommen soll. Somit fallen unbeabsichtigte Änderungen der Engine sofort auf.

Die Frontend Unit Tests umfassen die einfachen Rechnungsfunktionen, wie z.B. ob die Punkteberechnung, wie viele bis zum nächsten Score-Band fehlen, richtig funktioniert, sowie ob ARIA-Labels für Screenreader richtig gesetzt sind.

Als letztes gibt es auch E2E Playwright tests. Da diese sehr lange brauchen, sind diese nicht in großen Mengen vorhanden. Sie steuern einen virtuellen Browser, und klicken sich wie ein menschlicher Nutzer durch die Anwendung. So wird z.B. getestet, ob ein Konto erfolgreich angelegt werden kann, die Onboarding Schritte durchlklickbar sind und das Dashboard korrekt den Startscore lädt.

### Qualitätssicherung

Da der Code zu einem Großteil von KI geschrieben wurde ist die Qualitätssicherung besonders sicher. Wenn KI halluziniert reichen keine einfach bitten an die KI, das nicht zu tun, sondern nur handfeste Prüfungen. Während die zuvor beschriebenen Tests dazu gehören, sind auch keine impliziten `any`-types im Code erlaubt. Zudem stellt der Lintere (TODO: Welcher Linter??) sicher, dass die Architketur eingehalten wird und keine toten Imports vorhanden sind, selbst wenn der Code selbst dabei keinen Fehler schmeißen würde. So bleibt Code lesbar, einfach und auch von Menschen wartbar. Erst wenn all diese Schritte erfolgreich durchlaufen sind, ist ein Mergen möglich. Als zusätzlichen Schritt hatten wir zudem immer die Notwendigkeit von mindestens einem Review, dass zusätzlich zu allen zuvor genannten Gates durchgeführt wird, und überprüft, ob die in den Issues genannten Anforderungen erfüllt sind, die bereits gegebene Architektur erfüllt sind.
